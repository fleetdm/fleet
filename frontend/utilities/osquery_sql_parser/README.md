# osquery_sql_parser

A standalone parser for the SQLite SQL flavor that osquery executes, used to
validate queries and extract table names in the browser.

The grammar is tightened to what osquery actually runs: **SELECT statements
only** (including CTEs, UNION, and VALUES inside CTEs). INSERT, UPDATE,
DELETE, CREATE, DROP, ALTER, ATTACH, etc. are parse errors by design.

## Provenance

`osquery_sql.pegjs` derives from
[sgress454/node-sql-parser](https://github.com/sgress454/node-sql-parser)
(Fleet's fork of
[taozhi8833998/node-sql-parser](https://github.com/taozhi8833998/node-sql-parser),
Apache-2.0 — see `LICENSE`) at tag `5.4.0-fork.2`.

## Files

### Sourced

- `osquery_sql.pegjs` — the grammar.
- `index.ts` — the public wrapper (`astify`).
- `osquery_sql_parser.generated.d.ts` — type declarations for peggy.
- `osquery_sql_parser.tests.ts`, `corpus.tests.ts` — the tests files.
- `corpus.json` — the test corpus.

### Generated (DO NOT EDIT)

| File | Generated by |
|---|---|
| `osquery_sql_parser.generated.js` | `yarn generate:osquery-sql-parser`, which runs the lockfile-pinned peggy over `osquery_sql.pegjs`. `make generate-osquery-sql-parser` does the same. |

This is the only generated file. It is built on demand rather than checked in, before
anything that consumes it, by the `pretest`, `pretest:ci`, `prelint`,
`prestorybook` and `prebuild-storybook` yarn hooks and the `generate-js`,
`generate-ci` and `generate-dev` make targets. Regenerate it by hand when you
want to read the generated code, or after editing the grammar if you run jest
directly - an IDE test runner bypasses the yarn hooks and would use the stale
parser.

Always regenerate through the yarn script, never a global `npx peggy`: output
differs between peggy versions.

## The test corpus

`corpus.json` is a hand-maintained fixture. **When you fix or
find a parser bug, add the query to it** — that is how the corpus grows.

It was seeded once from every query shipped in this repo (standard query
library, CIS packs, GitOps) plus hand-written grammar cases, reduced to
one query per distinct SQL *shape*. 

Worth knowing when adding cases: what earns a new entry is a *shape* or token
sequence not already covered, not a new registry path or table name. Variety
that affects parsing does count - an escaped quote, a backslash, a newline
inside a string, non-ASCII, an empty or very long literal, double-quoted or
backtick quoting — as does syntax that differs only in comments, semicolons, or
optional keywords (`JOIN` vs `INNER JOIN`, alias with or without `AS`).

Entries omit fields at their defaults, and `query` is the only required one:

```json
{"query": "SELECT 1 FROM location_services WHERE enabled = 1;"}
{"name": "INSERT", "query": "INSERT INTO users (name) VALUES ('Mike')",
 "expect": "reject", "note": "osquery is read-only; only SELECT statements can run"}
```

- no `expect` means the query **must parse** (the vast majority)
- `expect: "reject"` means the parser must not accept it, and carries either
  `knownFailure` — valid osquery SQL the grammar cannot parse yet, so closing
  the gap means updating the entry — or a `note` explaining the rejection:
  broken SQL, or a deliberate exclusion such as non-SELECT statements and bind
  parameters nothing in Fleet can bind
- `name` is optional, and worth setting on a case you add so a failure says
  what it was testing. The seeded repo queries carry none; a failure on those
  reports the SQL itself, which is what you need to debug a parse error anyway.

## Making a change

```
reproduce → add a failing case to corpus.json → edit osquery_sql.pegjs → test
```

The `/fix-sql-parser` Claude Code skill runs these steps for a given query.

1. **Reproduce.** Run the failing SQL through the grammar directly:
   ```sh
   yarn --silent peggy -t "SELECT ... the failing query ..." frontend/utilities/osquery_sql_parser/osquery_sql.pegjs
   ```
   On failure this prints a `SyntaxError` with a `location` (line/column) and
   an expected-token list that identify the grammar rule to widen. First
   confirm the SQL is valid in real SQLite (`sqlite3` CLI) — if SQLite
   rejects it too, fix the query, not the grammar.
2. **Add the failing query to `corpus.json`, and watch it fail.** Add an entry
   with a `name` and the SQL, then run the tests (step 4) and confirm the
   corpus test fails, naming your entry. A test that fails for the right
   reason before you touch the grammar is what proves the fix works.

   - a query that *should* parse: add `{"name": "...", "query": "..."}`, with
     no `expect`
   - a query that should be *rejected*: add `"expect": "reject"` and a `note`
     saying why
   - if the query is already in the corpus as a `knownFailure`, delete its
     `knownFailure` and `expect` fields now, not after. Left alone that entry
     asserts the gap still exists, so it passes until you fix the grammar and
     then fails — the opposite of what you want. Removing the fields first
     turns it into the failing test
3. **Edit the grammar.** Rules read like BNF: `rule = alt1 / alt2 { action }`.
   The action blocks build the AST, so the grammar is also the AST-shape
   documentation. Notes: `'FOO'i` matches case-insensitively, `__` is optional
   whitespace/comments, and alternation order matters (longest match first).
   Do not re-add DDL/DML alternatives to `crud_stmt`. If a change produces a
   new AST node shape, check whether `sql_tools.ts` needs to learn it.
4. **Test.** `yarn test frontend/utilities/osquery_sql_parser frontend/utilities/sql_tools.tests.ts frontend/components/forms/validators/validate_query`

   `yarn test` regenerates the parser from the grammar first, via the `pretest`
   hook — always through the pinned peggy from the lockfile. The one thing that
   does NOT regenerate it is invoking jest directly, e.g. from an IDE test
   runner: after a grammar edit, run `make generate-osquery-sql-parser` first
   or your run uses the stale parser.
5. **Commit** the grammar and `corpus.json`. The generated parser is
   gitignored — there is nothing else to commit.

## Pulling fixes from upstream

Diff upstream's `pegjs/sqlite.pegjs` against tag `5.4.0-fork.2` in the fork
repo and port the hunks manually onto `osquery_sql.pegjs` here.

No vulnerability scanner tracks this vendored grammar — it is not declared in
any manifest, so upstream advisories will not surface automatically. Check
node-sql-parser's advisories by hand when porting, and judge whether they touch
the sqlite grammar rules still present here.
